# Alpaca

Два задания Jenkins заменяют прежний цикл в чате. Cursor в них только меняет код. Git, комментарии, публикация компонент, сборка и тесты — шаги Jenkins.

Субагент тут не граница. У субагента остаются те же команды, включая git. Граница — обычный step задания: перед Cursor в `PATH` подставляются заглушки `git` и `gh`, а в конфиг CLI записывается запрет этих команд.

## Задания

Их нужно один раз создать вручную. Репозиторий сам их на сервере не заводит. Оба — Pipeline from SCM, ветка `*/main`, credentials `gitalpaca`, agent `windows`.

| Имя | Jenkinsfile |
| --- | --- |
| `AlpacaWatch` | `ci/pipelines/alpaca_watch.jenkinsfile` |
| `AlpacaWork` | `ci/pipelines/alpaca_work.jenkinsfile` |

Jenkins читает Jenkinsfile из `main`. Пока эти файлы не на `main`, задания их не увидят. Расписание `H * * * *` (раз в час) появляется после первого запуска этого Jenkinsfile. Кнопка ручного запуска есть сразу: у задания нет параметров.

На windows-агенте должны быть `gh`, уже авторизованный в `Bayselonarrend/OpenIntegrations`, и Cursor CLI: команда `agent` или `cursor-agent` в `PATH`.

## Что делает watcher

Раз в час берёт один открытый issue, назначенный на `VitalyTheAlpaca`. Закрытые не рассматриваются. Если открытых несколько, берётся первый, который вернул `gh`.

- Нет открытого PR из ветки `alpaca/<номер>` — запускает `AlpacaWork` с причиной `new` и не ждёт его.
- PR уже есть — смотрит комментарии issue, PR и ревью. Свои комментарии задания помечены `<!-- alpaca -->` и сами по себе новый цикл не открывают. Новый цикл из-за комментария открывается, только если комментарий человека новее метки `<!-- alpaca-start -->`.
- Если `AlpacaWork` уже идёт или стоит в очереди, watcher ничего не запускает.

## Что делает worker

Ветка `alpaca/<номер>`. Если issue уже закрыт, задание останавливается до правок и нового цикла. PR в `main` открывается после первого коммита: у пустой ветки, совпадающей с `main`, GitHub PR не создаёт. Если Cursor ничего не изменил, задание пишет об этом в issue и не открывает PR. Когда PR уже есть, метка цикла пишется в него.

1. Cursor меняет код по тексту issue и всем комментариям. Причина `build` или `tests` не заменяет задачу: последнее замечание нужно учесть и идти дальше по задаче. Тесты в этом запуске не пишутся.
2. Отдельный запуск Cursor, уже без контекста реализации, смотрит, изменился ли публичный API. Если да, добавляет или правит тесты по правилам из `AGENTS.md`. Проверка следует задаче и контракту метода, а не текущей реализации. Затем Jenkins коммитит и пушит. Если файлы не изменились, цикл останавливается.
3. `src/addins/publish-addins.bat` запускается после каждого такого коммита. В начале задания zip уже подтянуты из `origin/addins`, Cursor при необходимости перезаписывает zip своей компоненты через `release.bat`. Повторный sync перед публикацией не делается: он заменил бы свежий zip старым.
4. `BigFloppa` с `BRANCH` этой ветки, `UPLOAD_ARTIFACTS=false` и `SKIP_DB_UPDATE=true`.
5. Сборка упала — Cursor пишет в PR, в чём дело. Задание запускает себя ещё раз (`wait: false`) и само завершается успешно. Новый запуск снова читает issue и все комментарии.
6. Сборка прошла — Cursor выбирает тесты OneScript RU по изменённым методам. Jenkins их запускает. Упали тесты этих методов — комментарий и новый запуск. Успех или падение не из этого кода — комментарий, нового запуска нет.

Потолок — 8 циклов (`MAX_CYCLE`). Дальше задание пишет об этом в PR и не запускает себя снова.

`SKIP_DB_UPDATE` у `BigFloppa` по умолчанию выключен, обычные запуски по-прежнему обновляют базу. Параметр появляется после первого прогона `BigFloppa`, который прочитал Jenkinsfile с этим флагом. До этого Alpaca не сможет передать его.
