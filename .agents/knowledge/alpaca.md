# Alpaca

Два задания Jenkins заменяют прежний цикл в чате. Cursor в них только меняет код. Git, комментарии, публикация компонент, сборка и тесты — шаги Jenkins.

Субагент тут не граница. У субагента остаются те же команды, включая git. Граница — обычный step задания: перед Cursor в `PATH` подставляются заглушки `git` и `gh`, а в конфиг CLI записывается запрет этих команд.

## Задания

Их нужно один раз создать вручную. Репозиторий сам их на сервере не заводит. Оба — Pipeline from SCM, ветка `*/main`, credentials `gitalpaca`, agent `windows`.

| Имя | Jenkinsfile |
| --- | --- |
| `AlpacaWatch` | `ci/pipelines/alpaca_watch.jenkinsfile` |
| `AlpacaWork` | `ci/pipelines/alpaca_work.jenkinsfile` |

Jenkins читает Jenkinsfile из `main`. Пока эти файлы не на `main`, задания их не увидят. Расписание `H/5 * * * *` (раз в пять минут) появляется после первого запуска этого Jenkinsfile. Кнопка ручного запуска есть сразу: у задания нет параметров. Проверка, которая никого не запустила, через несколько секунд удаляется из истории. Если удаление не сработало, в истории остаются последние 40 сборок.

На windows-агенте должны быть `gh` и Cursor CLI: команда `agent` или `cursor-agent` в `PATH`. Запуск выставляет `NODE_USE_SYSTEM_CA=1`, чтобы Node внутри CLI доверял корневым сертификатам Windows. Вызовы `gh` получают `GH_TOKEN` из пароля credentials `gitalpaca`, поэтому комментарии и PR создаются от `VitalyTheAlpaca`, а не от учётки, под которой `gh` залогинен на агенте. У этого токена должны быть права писать issues и pull requests.

## Что делает watcher

Раз в пять минут берёт один открытый issue, назначенный на `VitalyTheAlpaca`. Закрытые не рассматриваются. Если открытых несколько, берётся первый, который вернул `gh`.

- Нет открытого PR из ветки `alpaca/<номер>` — запускает `AlpacaWork` с причиной `new` и не ждёт его.
- PR уже есть — смотрит комментарии issue, PR, ревью и замечания к строкам. Свои комментарии задания помечены `<!-- alpaca -->` и сами по себе новый цикл не открывают. Новый цикл из-за комментария открывается, только если комментарий `bayselonarrend` новее метки `<!-- alpaca-start -->` и на нём ещё нет реакции 👀 от `VitalyTheAlpaca`. Чужие комментарии цикл не запускают.
- Если на контроллере уже идёт любая другая сборка, кроме самого `AlpacaWatch`, watcher ничего не запускает. Список берётся из каталога Jenkins рядом с workspace: у задания `lastBuild` ещё не совпал с `lastCompletedBuild`. Свою сборку скрипт не считает. Если каталог Jenkins не найден, цикл тоже не запускается.

## Что делает worker

Ветка `alpaca/<номер>`. После переключения скрипты `ci/alpaca` берутся с `origin/main` и в коммит ветки не попадают. Если issue уже закрыт, задание останавливается до правок и нового цикла. PR в `main` открывается после первого коммита: у пустой ветки, совпадающей с `main`, GitHub PR не создаёт. Если после правки кода дерево git чистое и в `ci/alpaca/out/answer.md` есть ответ на вопрос, задание публикует этот ответ и останавливается. Если ответа нет, пишет, что код не менялся. В обоих случаях нет коммита, публикации, сборки и тестов. Когда цикл открыт из-за комментария, бот ставит 👀 на каждый такой комментарий и не пишет «Вижу комментарий, начинаю обработку.». В остальных случаях метка цикла пишется в PR, а если его ещё нет — после первого коммита.

1. Cursor меняет код по тексту issue и комментариям. Указания даёт `bayselonarrend`. Чужие комментарии в issue остаются контекстом и не отменяют задачу. В PR заданиями считаются только его комментарии и ревью. Причина `build` или `tests` не заменяет задачу: последнее замечание нужно учесть и идти дальше по задаче. Тесты в этом запуске не пишутся.
2. Если код изменился, отдельный запуск Cursor, уже без контекста реализации, смотрит, изменился ли публичный API. Если да, добавляет или правит тесты по правилам из `AGENTS.md`. Проверка следует задаче и контракту метода, а не текущей реализации. Перед коммитом Jenkins запускает `DictionariesMethods.os`. Если скрипт завершился с кодом 111, отдельный запуск Cursor заполняет пустые значения в `service/dictionaries/en.json`: идентификатор без пробелов остаётся без пробелов. Скрипт запускается ещё раз и должен завершиться с кодом 0. Затем Jenkins коммитит как `Альпака Виталий` (`vitaly.alpaca@openintegrations.dev`, та же пара, что в сборке main) и пушит. Текст берётся из `ci/alpaca/out/commit-msg.txt`, который Cursor пишет в фазе правки. Если файла нет, в коммит попадает заголовок issue. Если после этого шага дерево снова чистое, цикл останавливается так же, как в пункте выше.
3. `src/addins/publish-addins.bat` после коммита публикует zip в `addins-alpaca-<номер>`, не в общую `addins`. Имя плоское: ветка `addins` уже есть, и ref `addins/alpaca/<номер>` GitHub отклоняет как directory file conflict. В начале задания zip берутся из этой ветки, а если её ещё нет — из `origin/addins`. Cursor при необходимости перезаписывает zip своей компоненты через `release.bat`. Повторный sync перед публикацией не делается: он заменил бы свежий zip старым. Сборка и тесты этого цикла синхронизируют ту же ветку через параметр `ADDINS_BRANCH` (по умолчанию у заданий `addins`). Раз в сутки `AlpacaAddins` удаляет `addins-alpaca-<номер>`, если ветки `alpaca/<номер>` уже нет.
4. `BigFloppa` с `BRANCH` этой ветки, `UPLOAD_ARTIFACTS=false` и `SKIP_DB_UPDATE=true`.
5. Сборка упала — Cursor пишет в PR, в чём дело. Задание запускает себя ещё раз (`wait: false`) и само завершается успешно. Новый запуск снова читает issue и все комментарии.
6. Сборка прошла — Cursor выбирает тесты OneScript RU по изменённым методам. Jenkins добавляет парный EN (`OpiOsWinEn`) и запускает оба. Упали тесты этих методов — комментарий и новый запуск. Если RU прошёл, а EN упал, искать причину надо в новых переводах `service/dictionaries/en.json` и в коде, который этот перевод уже затронул. Успех или падение не из этого кода — комментарий, нового запуска нет. Если разбор не завершился, а выбранные задания упали, в комментарий попадает хвост лога и запускается следующий цикл. Лог читается из файла сборки Jenkins. Комментарий, который не удалось отправить, завершает прогон ошибкой. Вызовы `gh` повторяются до четырёх раз.

Потолок — 8 циклов (`MAX_CYCLE`). Дальше задание пишет об этом в PR и не запускает себя снова.

`SKIP_DB_UPDATE` у `BigFloppa` по умолчанию выключен, обычные запуски по-прежнему обновляют базу. Параметр появляется после первого прогона `BigFloppa`, который прочитал Jenkinsfile с этим флагом. До этого Alpaca не сможет передать его.
