# Alpaca

Задания Jenkins заменяют прежний цикл в чате. Cursor в них только меняет код или пишет ревью. Git, комментарии, публикация компонент, сборка и тесты — шаги Jenkins.

Субагент тут не граница. У субагента остаются те же команды, включая git. Граница — обычный step задания: перед Cursor в `PATH` подставляются заглушки `git` и `gh`, а в конфиг CLI записывается запрет этих команд.

## Задания

Их нужно один раз создать вручную. Репозиторий сам их на сервере не заводит. Все — Pipeline from SCM, ветка `*/main`, agent `windows`. SCM-credentials у Watch, очистки веток и Виталия — `gitalpaca`, у Полины — `gitpolina`, у Руслана — `gitruslan`.

Имя задания не может содержать `|`. В интерфейсе у папки заголовок `Alpaca | Агентская разработка`, у вложенных — `Alpaca | Виталий`, `Alpaca | Полина` и `Alpaca | Руслан`.

| Имя | Заголовок | Jenkinsfile |
| --- | --- | --- |
| `Alpaca/AlpacaWatch` | общая точка входа | `ci/pipelines/alpaca_watch.jenkinsfile` |
| `Alpaca/Vitaly/AlpacaWork` | `Alpaca \| Виталий` | `ci/pipelines/alpaca_work.jenkinsfile` |
| `Alpaca/Ruslan/AlpacaReview` | `Alpaca \| Руслан` | `ci/pipelines/alpaca_review.jenkinsfile` |
| `Alpaca/Polina/AlpacaTest` | `Alpaca \| Полина` | `ci/pipelines/alpaca_test.jenkinsfile` |
| `Alpaca/AlpacaAddins` | очистка веток компонент | `ci/pipelines/alpaca_addins.jenkinsfile` |

Jenkins читает Jenkinsfile из `main`. Пока эти файлы не на `main`, задания их не увидят. Расписание `H/5 * * * *` (раз в пять минут) появляется после первого запуска этого Jenkinsfile. Кнопка ручного запуска есть сразу: у задания нет параметров. Проверка, которая никого не запустила, через несколько секунд удаляется из истории. Если удаление не сработало, в истории остаются последние 40 сборок.

На windows-агенте должны быть `gh` и Cursor CLI: команда `agent` или `cursor-agent` в `PATH`. Запуск выставляет `NODE_USE_SYSTEM_CA=1`, чтобы Node внутри CLI доверял корневым сертификатам Windows. У каждого агента свой credentials: Виталий — `gitalpaca`, Полина — `gitpolina`, Руслан — `gitruslan`. Комментарии идут от логина этого токена. У токенов должны быть права писать issues и pull requests.

Профили лежат в `ci/alpaca/agents/<id>/`: `agent.json` (логин, почта, credentials, модель, задание Jenkins, на чьи сообщения реагировать), `prompt.md` (кто это, задача, границы), `mcp.json` (какие MCP подключать). Скачивание jar по-прежнему общее, из `ci/config_global.json`. В сессию попадает только `mcp.json` этого агента. Сейчас у всех трёх подключён синтаксис-помощник. Модель передаётся в Cursor CLI как `--model`.

| id | Логин | Роль |
| --- | --- | --- |
| `vitaly` | `VitalyTheAlpaca` | Автор. Реагирует только на `@VitalyTheAlpaca` от `bayselonarrend`, `RuslanTheAlpaca` и `PolinaTheAlpaca`. |
| `polina` | `PolinaTheAlpaca` | Тесты. Реагирует только на `@PolinaTheAlpaca` от владельца, Виталия и Руслана. В тот же PR коммитит тесты и зовёт Руслана, когда функционально всё в порядке. |
| `ruslan` | `RuslanTheAlpaca` | Ревьюер. Код не меняет. Реагирует на `@RuslanTheAlpaca` от владельца, Виталия и Полины. |

## Что делает watcher

Раз в пять минут обходит агентов. Назначение issue никого не запускает. Для каждого агента ищет открытые упоминания его логина и берёт первое, где комментарий, ревью или замечание к строке новее его метки `<!-- alpaca-start -->`, автор входит в `reactTo`, и на записи ещё нет реакции 👀 этого агента. Упоминание в обычном issue запускает работу по его номеру. Упоминание в PR запускает работу, только если голова PR — ветка `alpaca/<номер>`.

- Свои комментарии задания помечены `<!-- alpaca -->` и сами по себе новый цикл не открывают. Нужно именно обращение `@логин`. Действует последнее такое обращение: более ранний вызов не стартует, если после него позвали другого.
- Виталий и Полина не стартуют, пока на контроллере идёт чужая сборка. В одном проходе на одно issue встаёт только один из них: если упомянуты оба, первым идёт Виталий. Руслан ждёт, пока для этого issue не закончатся правка, сборка и тесты, и не стартует в том же проходе, где уже встал автор или Полина. Список берётся из каталога Jenkins рядом с workspace: у задания `lastBuild` ещё не совпал с `lastCompletedBuild`. Свою сборку скрипт не считает. Если каталог Jenkins не найден, цикл тоже не запускается.

## Что делает worker

Ветка `alpaca/<номер>`. После переключения скрипты `ci/alpaca` берутся с `origin/main` и в коммит ветки не попадают. Если issue уже закрыт, задание останавливается до правок и нового цикла. Коммит в ветку не открывает PR. Черновик PR создаёт задание, только если Виталий записал `ci/alpaca/out/open-pr.txt` со строкой `yes`: так он отмечает прямую просьбу владельца создать или открыть pull request. Сам он `git` и `gh` не вызывает. У пустой ветки, совпадающей с `main`, GitHub PR не создаёт. Ревьюером ставится `RuslanTheAlpaca`. Когда сборка прошла, результат тестов — прошли, упали или не нужны — задание упоминает `@PolinaTheAlpaca` и не упоминает Руслана. Повторный цикл из-за упавших тестов само не запускает: Полина читает результат и, если править должен автор, зовёт `@VitalyTheAlpaca`. Если функционально всё в порядке, её комментарий содержит `@RuslanTheAlpaca`. Владелец тоже может позвать Руслана сам. Руслан пишет вывод и, если замечаний нет, ставит approving review и упоминает `@VitalyTheAlpaca`. Виталий на этом упоминании снимает черновик командой `gh pr ready`. Пока одобрения нет, PR остаётся черновиком. Если пока задание шло, появилось новое обращение, оно не зовёт следующего и не запускает ещё один цикл: `@` из подготовленного комментария снимается, текст остаётся, а Watch берёт новое обращение. Одно и то же обращение второй раз не берётся: на него ставится 👀, в том числе когда PR ещё нет. Если сборка уже стоит в очереди и к её старту 👀 уже есть, она останавливается и ничего не пишет. Просьба посмотреть, проверить или оценить без просьбы исправить код заканчивается ответом без правок: первая строка говорит, актуален ли issue, есть ли проблема и нужно ли её чинить. Если после правки кода дерево git чистое и в `ci/alpaca/out/answer.md` есть ответ на вопрос, задание публикует этот ответ и останавливается. Если ответа нет, пишет, что код не менялся. В обоих случаях нет коммита, публикации, сборки и тестов. Ручной запуск с причиной `resume` код не меняет: заново собирает zip компонент, изменённых в ветке, публикует их, гоняет сборку и тесты и зовёт Полину. Когда цикл открыт из-за комментария, бот ставит 👀 на каждый такой комментарий и не пишет «Вижу комментарий, начинаю обработку.». В остальных случаях метка цикла пишется в PR, а если его ещё нет — после первого коммита.

1. Cursor меняет код по тексту issue и комментариям. Указания даёт `bayselonarrend`. Замечания `RuslanTheAlpaca` нужно учесть. Чужие комментарии в issue остаются контекстом и не отменяют задачу. Причина `build` или `tests` не заменяет задачу: последнее замечание нужно учесть и идти дальше по задаче. Тесты в этом запуске не пишутся.
2. Если код изменился, отдельный запуск Cursor, уже без контекста реализации, смотрит, изменился ли публичный API. Если да, добавляет или правит тесты по правилам из `AGENTS.md`. Проверка следует задаче и контракту метода, а не текущей реализации. Перед коммитом Jenkins запускает `DictionariesMethods.os`. Если скрипт завершился с кодом 111, отдельный запуск Cursor заполняет пустые значения в `service/dictionaries/en.json`: идентификатор без пробелов остаётся без пробелов. Скрипт запускается ещё раз и должен завершиться с кодом 0. Затем Jenkins коммитит как `Альпака Виталий` (`vitaly.alpaca@openintegrations.dev`, та же пара, что в сборке main) и пушит. Текст берётся из `ci/alpaca/out/commit-msg.txt`, который Cursor пишет в фазе правки. Если файла нет, в коммит попадает заголовок issue. Если после этого шага дерево снова чистое, цикл останавливается так же, как в пункте выше.
3. `src/addins/publish-addins.lua` после коммита публикует zip в `addins-alpaca-<номер>`, не в общую `addins`. Имя плоское: ветка `addins` уже есть, и ref `addins/alpaca/<номер>` GitHub отклоняет как directory file conflict. В начале задания zip берутся из этой ветки, а если её ещё нет — из `origin/addins`. Cursor при необходимости перезаписывает zip своей компоненты через `release.bat`. Повторный sync перед публикацией не делается: он заменил бы свежий zip старым. Сборка и тесты этого цикла синхронизируют ту же ветку через параметр `ADDINS_BRANCH` (по умолчанию у заданий `addins`). Раз в сутки `AlpacaAddins` удаляет `addins-alpaca-<номер>`, если ветки `alpaca/<номер>` уже нет.
4. `BigFloppa` с `BRANCH` этой ветки, `UPLOAD_ARTIFACTS=false` и `SKIP_DB_UPDATE=true`.
5. Сборка упала — Cursor пишет в PR, в чём дело. Задание запускает себя ещё раз (`wait: false`) и само завершается успешно. Новый запуск снова читает issue и все комментарии.
6. Сборка прошла — Cursor выбирает тесты OneScript RU по изменённым методам. Jenkins добавляет парный EN (`OpiOsWinEn`) и запускает оба. Упали тесты этих методов — комментарий и новый запуск. Если RU прошёл, а EN упал, искать причину надо в новых переводах `service/dictionaries/en.json` и в коде, который этот перевод уже затронул. Успех или падение не из этого кода — комментарий, нового запуска нет. Если разбор не завершился, а выбранные задания упали, в комментарий попадает хвост лога и запускается следующий цикл. Лог читается из файла сборки Jenkins. Комментарий, который не удалось отправить, завершает прогон ошибкой. Вызовы `gh` повторяются до четырёх раз.

Потолок — 8 циклов (`MAX_CYCLE`). Дальше задание пишет об этом в PR и не запускает себя снова.

`SKIP_DB_UPDATE` у `BigFloppa` по умолчанию выключен, обычные запуски по-прежнему обновляют базу. Параметр появляется после первого прогона `BigFloppa`, который прочитал Jenkinsfile с этим флагом. До этого Alpaca не сможет передать его.
