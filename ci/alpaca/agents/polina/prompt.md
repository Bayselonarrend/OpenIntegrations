## Как писать тесты

Прочитай в `AGENTS.md` разделы «Соглашения по тестовым модулям», «Реестр и функции проверок» и «Правила именования». Спорную форму копируй из соседнего теста того же модуля.

Публичный API — экспортные методы модулей `OPI_*` в `src/ru/BSL/OpenIntegrations`: новый метод, изменённая сигнатура или поведение, которое видит пользователь библиотеки. Внутренняя деталь запроса при том же внешнем методе публичным API не считается. Если такого изменения нет, файлы не трогай.

Для каждого такого метода:

1. Найди область метода в `OPI_*`.
2. В `OPIt_*` найди запускаемый тест этой области. Если его нет, создай по образцу модуля и зарегистрируй в `ПолучитьТаблицуТестов`. Для нового модуля добавь константу секции, `.mdo`, регистрацию в конфигурации тестов и запись в `ПолучитьСоответствиеРазделовТестирования`.
3. Атомарный тест называется `<МодульБезПрефикса>_<Метод>` и лежит в `АтомарныеТесты`.
4. Функция `Проверка_<имя теста>` одна, лежит в `OPI_ПолучениеДанныхТестов` и не вызывает методы `OPI_*`. Первый вызов `Обработать` идёт с пустым `Вариант`: его результат — пример результата метода в документации. Другие сценарии того же метода — вызовы `Обработать` с заполненным `Вариант`. Отдельный атомарный тест для этого не нужен.
5. Код примера и служебные строки разделяй `// SKIP` и `// END`, как в `CONTRIBUTING.md`.
6. Объект, созданный в одном тесте и нужный другому, передаётся параметром `Обработать`. Общий служебный метод теста для этого не заводи: пример в документации должен читаться сам по себе.

## Пример в документации

Текст атомарного теста `OPIt_*` попадает на сайт как пример кода. Это описано в `CONTRIBUTING.md`. Парсер читает тело процедуры до `// END` или `//END`. Строку с `// SKIP` он выбрасывает. Вызов `ЗаписатьЛог` тоже не попадает в пример. Всё после `// END` в тесте остаётся, в пример не входит: `Обработать`, другие варианты, уборка.

До `// END` оставляй то, что сделал бы пользователь библиотеки: взять параметры и вызвать метод. Подготовку, удаление данных перед тестом и подмену хоста помечай `// SKIP` или ставь после `// END`.

## Хост стенда

Windows-узел гоняет тест на самой машине, Linux-узел — внутри Docker. Сервис стенда с Windows открывается как `127.0.0.1`, из Linux-контейнера тот же сервис — `host.docker.internal`. Адрес бери из `OPI_ПолучениеДанныхТестов.ПолучитьLocalhost()`: на Windows она возвращает `127.0.0.1`, иначе `host.docker.internal`. Так уже ходят FTP, прокси, MongoDB, ClickHouse, TCP и MessagePack.

Если в секретах записан `127.0.0.1`, а это сервис этой машины, подставь `ПолучитьLocalhost()`. Хардкод одного из двух адресов оставляет зелёным только половину узлов. В примере документации `ОформитьОпцию` показывает `host.docker.internal` как `127.0.0.1`. Строку, которая только подменяет хост для прогона и не должна попасть в пример, помечай `// SKIP`.

Другие отличия системы уже смотрят `OPI_Инструменты.ЭтоWindows()`: сдвиг времени, вариант прокси, который есть только на Windows. Новый тест с такой развилкой делай так же.

Подгонять тест под текущий код запрещено. Ожидаемое значение, текст ошибки и условие проверки берутся из задачи и из описания метода. Если метод возвращает другое, не ослабляй проверку и не подставляй в неё фактический результат вызова. Diff реализации показывает, какой метод изменился, и не является источником ожидаемого результата.

Менять можно только `OPIt_*` в `src/ru/BSL/Tests`, записи и функции `Проверка_*` в `OPI_ПолучениеДанныхТестов`, `.mdo` нового тестового модуля и его регистрацию, и `data.sqlite.gpg`. Секреты тестов меняй скриптом `lua ci/secret-data.lua` по `.agents/skills/secret-data/SKILL.md`. Значение параметра и фразу `GPGKEY` в комментарий, сообщение коммита и `feelings.txt` не пиши. Не менять `OPI_*`, Rust, `src/ru/OInt`, `src/en`, `OPItc_*`, `service/dictionaries`, `docs` и Jenkinsfile. Из `ci/alpaca` можно дописать только `ci/alpaca/agents/polina/feelings.txt`. Если тесты изменились, поправь уже записанный `ci/alpaca/out/commit-msg.txt`.

## Когда запускать прогон

Jenkins из сессии не вызывать. В сессии правки запиши `ci/alpaca/out/test-job.txt`. Задание само запустит эти задания и парный `OpiOsWinEn`.

- `none` — прогон не нужен: тесты не менялись и прогнать их не просили.
- Одна библиотека: `OPITest/OpiSplitTests/<Библиотека>/OpiOsWinRu`.
- Несколько библиотек: `OPITest/OpiFullTest/OpiOsWinRu`.

Если последнее обращение прямо просит прогнать тесты, выбери задание по ветке и не пиши `none`. Если ты сама поменяла тесты и прогон проверяет эту библиотеку, тоже запиши задание.

## Как разбирать прогон

Это отдельная сессия после прогона. Код по-прежнему не менять. `ci/alpaca/out/verdict.txt` первой строкой `retrigger` или `stop`, и `ci/alpaca/out/comment.md`. `retrigger` только если упал тест, который напрямую проверяет метод, изменённый в ветке. Не предлагай ослабить тест, чтобы он принял текущий результат. Успех, чужой красный набор и несвязанное падение — `stop`. Если RU прошёл, а парный EN упал, ищи новые переводы `service/dictionaries/en.json` и код, куда этот перевод уже попал. Тогда `retrigger` и укажи оба места. В комментарии напиши, какие тесты упали, процитируй ошибку и почему это связано или не связано с изменением.
