## Как писать тесты

Прочитай в `AGENTS.md` разделы «Соглашения по тестовым модулям», «Реестр и функции проверок» и «Правила именования». Спорную форму копируй из соседнего теста того же модуля.

Публичный API — экспортные методы модулей `OPI_*` в `src/ru/BSL/OpenIntegrations`: новый метод, изменённая сигнатура или поведение, которое видит пользователь библиотеки. Внутренняя деталь запроса при том же внешнем методе публичным API не считается. Если такого изменения нет, файлы не трогай.

Для каждого такого метода:

1. Найди область метода в `OPI_*`.
2. В `OPIt_*` найди запускаемый тест этой области. Если его нет, создай по образцу модуля и зарегистрируй в `ПолучитьТаблицуТестов`. Для нового модуля добавь константу секции, `.mdo`, регистрацию в конфигурации тестов и запись в `ПолучитьСоответствиеРазделовТестирования`.
3. Атомарный тест называется `<МодульБезПрефикса>_<Метод>` и лежит в `АтомарныеТесты`.
4. В нём до `//END` есть один вызов `Обработать` с пустым `Вариант`. Это пример для документации. Функция `Проверка_<имя теста>` одна, лежит в `OPI_ПолучениеДанныхТестов` и не вызывает методы `OPI_*`.
5. Другие сценарии того же метода — дополнительные вызовы `Обработать` с заполненным `Вариант` после `//END`. Отдельный атомарный тест для этого не нужен.
6. Объект, созданный в одном тесте и нужный другому, передаётся параметром `Обработать`. Общий служебный метод теста для этого не заводи.

Подгонять тест под текущий код запрещено. Ожидаемое значение, текст ошибки и условие проверки берутся из задачи и из описания метода. Если метод возвращает другое, не ослабляй проверку и не подставляй в неё фактический результат вызова. Diff реализации показывает, какой метод изменился, и не является источником ожидаемого результата.

Менять можно только `OPIt_*` в `src/ru/BSL/Tests`, записи и функции `Проверка_*` в `OPI_ПолучениеДанныхТестов`, `.mdo` нового тестового модуля и его регистрацию. Не менять `OPI_*`, Rust, `src/ru/OInt`, `src/en`, `OPItc_*`, `service/dictionaries`, `docs` и Jenkinsfile. Из `ci/alpaca` можно дописать только `ci/alpaca/agents/polina/feelings.txt`. Если тесты изменились, поправь уже записанный `ci/alpaca/out/commit-msg.txt`.

## Как разбирать прогон

Код по-прежнему не менять.

- Выбор заданий: единственный файл `ci/alpaca/out/test-job.txt`. Правила в `.agents/skills/jenkins-verify/SKILL.md`. Пиши только OneScript RU. EN не пиши: Jenkins добавит парный `OpiOsWinEn`. Одна библиотека — `OPITest/OpiSplitTests/<Библиотека>/OpiOsWinRu`. Несколько или непонятно какая — `OPITest/OpiFullTest/OpiOsWinRu`. Нечего проверять — одна строка `none`.
- Разбор падения: `ci/alpaca/out/verdict.txt` первой строкой `retrigger` или `stop`, и `ci/alpaca/out/comment.md`. `retrigger` только если упал тест, который напрямую проверяет метод, изменённый в ветке. Не предлагай ослабить тест, чтобы он принял текущий результат. Успех, чужой красный набор и несвязанное падение — `stop`. Если RU прошёл, а парный EN упал, ищи новые переводы `service/dictionaries/en.json` и код, куда этот перевод уже попал. Тогда `retrigger` и укажи оба места. В комментарии напиши, какие тесты упали, процитируй ошибку и почему это связано или не связано с изменением.
